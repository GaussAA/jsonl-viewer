# webview

## Purpose

The front-end of the extension: a vanilla TypeScript app (no framework) bundled by esbuild into `dist/webview.js` (IIFE, `platform: 'browser'`, global `JlvWebview`, entry `webviewEntry.ts`). It runs inside the sandboxed VS Code webview under a nonce CSP and renders a paged record list (left), a lazy JSON tree detail view (right), a toolbar (search / filter / fields / follow-tail), and floating panels for editing, history, bad-line diagnostics and data profiling. All data comes from the extension host over `postMessage`; the webview never touches the file system.

`webviewEntry.ts` is the assembly layer: `main()` creates the `RpcBus`, the shared `AppState`, the UI components, and wires the domain modules together by dependency injection. Domain logic has been extracted out of `main()` into small `create*` factories so each can be unit-tested with fake deps.

## For AI Agents

### Working In This Directory

- **Browser platform only.** No `node:*` imports, no `fs`/`path`/`Buffer`. The bundle is built without externals, so a Node built-in would be pulled in or break at runtime. Currently no file here imports one. Allowed cross-boundary imports are `../constants.ts`, `../protocol/rpc.ts`, `../core/query.ts`, `../core/jsonSpan.ts`, `../core/replaceLogic.ts` (all browser-safe). Never import from `../host/` at runtime (type-only imports are erased).
- **CSP.** The page is served with `default-src 'none'; style-src ${cspSource} 'unsafe-inline'; script-src 'nonce-…'` (see `renderViewerHtml` in `src/extension.ts`). No inline `<script>`, no `onclick=` attributes, no `eval` / `new Function`, no remote resources. Styles go through `styles.ts` (`CSS_TEXT`), injected by `injectStyle()` in `webviewEntry.ts`. Do not add new `<style>` blocks elsewhere. `el.style.*` / `style.cssText` already appear in a few places (`toolbar.ts`, `virtualScroll.ts`, drawer animations), so keep such use to dynamic values only.
- **Bounded DOM.** Node count must stay O(page size), not O(file size). The list renders exactly `PAGE_SIZE = 20` cards; the record cache is an LRU capped at `CACHE_MAX_ENTRIES = 600`; the tree builds children lazily and previews large arrays (`LARGE_ARRAY_PREVIEW = 50`). A new feature that renders per-record or per-match elements must be paged or capped, and must say so in the UI when truncating.
- **Drop late responses.** Every async request is correlated by `requestId` (`RpcBus.request` returns `{ requestId, promise }`). Before applying a result, check the request is still current: compare `state.detailInFlight?.rid`, `state.inFlight` (`superseded` flag), `searchInFlight`, `filterInFlight`, or the `active*` handles. A superseded request settles immediately with `CancelledError` and any late reply is discarded in `RpcBus`. Do not apply a response without this check.
- **Pure logic vs DOM split.** This is a convention, verified for the files below, and tests rely on it:
  - `logic.ts`, `detailLogic.ts`, `editLogic.ts`, `profileLogic.ts`, `queryLogic.ts`, `appState.ts`, `utils.ts` (except `renderHighlight`) are pure: no `document` / `window` and no vscode API.
  - `*Ops.ts`, `queryActions.ts`, `persistence.ts`, `persistRestore.ts`, `navigation.ts`, `focusTarget.ts` have no DOM access. They take narrow `Pick<AppState, …>` subsets and callbacks through a `Deps` object. Keep it that way: do not hand them the whole state.
  - `*Panel.ts`, `toolbar.ts`, `detailTree.ts`, `virtualScroll.ts`, `columnLayout.ts` are DOM layers. Put decisions and wording into the matching pure module.
  - `selection.ts` is the one mixed file (state machine plus its action bar).
- **Single write points.** `state.selectedLine` is written only through `FocusTarget` (it keeps `detailRaw` in step; a mismatch would write line A's edit onto line B). Selection set lives only in `selection.ts`. Writes include `viewBaseline(state)` so the host can reject stale views. Field edits must go through the existing `EDIT_RECORD` / `REPLACE_FIELD` chain and use `detailRaw`, never re-serialized values.
- **XSS safety.** User data must never reach `innerHTML`. Render text with `textContent` / `createTextNode`, and highlight with `renderHighlight`. Existing `innerHTML` uses are static SVG icon constants only; keep it so. `escapeHtml` exists for the rare string-building case (`security.test.ts`).
- **Design contract.** Read `docs/DESIGN_SYSTEM.md` before any UI change (it is the single design contract and is written in Chinese). Key rules: all colors via `--vscode-*` variables or translucent white, no hard-coded theme colors; animate only `transform` / `opacity` (height only for a single subtree drawer, measured once); use the one easing curve and the three durations (fast 120 / base 180 / slow 280 ms); honor `prefers-reduced-motion`; page turn animates, selection only toggles a class (no list re-render); floating panels pop in 180 ms and fade out in 100 ms; narrow layout (<700px) must stack without horizontal overflow; verify dark and light themes. Its §7 checklist is the pass/fail gate for new UI.
- **Token names differ from the doc.** `DESIGN_SYSTEM.md` §1 names `--ease-out-expo`, `--dur-fast|base|slow`, but `styles.ts` actually defines `--jlv-ease`, `--jlv-dur-fast|base|slow`, plus `--jlv-space-*`, `--jlv-radius-*`, `--jlv-font-size-*` and semantic colors (`--jlv-good|warn|bad|info`, `--jlv-string|number|key|bool|null`). Use the `--jlv-*` names from the code. Likewise the doc says the left column is 340px while `columnLayout.ts` has `DEFAULT_LIST_WIDTH = 320`.
- **Webview-local state** (column width, collapsed flag) uses `acquireVsCodeApi().getState/setState`, not `localStorage`. User preferences (layout / filter / search) go through `persistence.ts` to the host.
- Add new constants (timeouts, caps) to `src/constants.ts`, not inline. Panels follow one lifecycle: a `create*Panel(deps)` factory returning a controller with `root`, `open`/`isOpen`, `dispose`; the entry appends `root` to `rootEl` and calls `dispose()` on teardown.
- Comments are mostly Chinese here; match that. Use explicit `.ts` import extensions and no constructor parameter properties.

### Testing Requirements

- Each module has a matching `__tests__/<name>.test.ts`, with two exceptions: `rpc.ts` is covered by `rpcBus.test.ts`, and `styles.ts` (a CSS string) has no test. Add or extend the test with each change; the CI coverage gate (lines 96 / branches 86 / functions 88) includes this directory.
- Pure modules: plain `node:test`, no DOM. DOM modules: use `setupWebviewDom()` from `__tests__/domHarness.ts`. See `__tests__/AGENTS.md`.
- Run `pnpm typecheck`, `pnpm test`, `pnpm lint`, `pnpm format:check`. After build-affecting changes run `pnpm compile` to confirm the IIFE still bundles (a Node built-in import would show up here).
- UI changes: walk the `DESIGN_SYSTEM.md` §7 checklist. jsdom cannot judge layout, animation or theming, so say explicitly what was not verified visually.

### Common Patterns

- Factory + injected deps: `createX(deps: XDeps): X`, where `deps.state` is a `Pick<AppState, …>`. Late-bound accessors (`getList`, `getToolbar`) break creation-order cycles inside `main()`.
- Long-running host work (scan, profile, replace, edit) shows a banner with progress and cancel. Cancel posts `CANCEL` and does **not** settle the local promise; the host reply says whether the result counts. The code that opened the banner must hide it on both success and failure.
- Partial or cancelled results must label themselves ("found so far", "result incomplete"). Never present a partial count as complete.
- Cap rather than truncate silently: select-all over the cap is refused, not clipped.
- After any row insert/delete: clear the whole record cache (line numbers shifted), re-fetch detail, and correct totals from the host's authoritative overview.
- Failure of auxiliary info (e.g. the bad-line badge) is silent; failure of a user-initiated write or scan is always reported.
