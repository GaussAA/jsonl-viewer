## Purpose

The extension-host data layer. `DataService` is the single facade the extension talks to: it lazily builds a sparse `LineIndex`, serves paged/summarised reads, runs search/filter/profile/bad-line scans, performs every disk write (single-line edit/insert/delete, batch delete, find/replace, field replace, undo/redo, orphan-backup recovery) and exports. Heavy scans (index build, search, filter) are delegated to an `IndexHost`: a `worker_threads` implementation (`dist/indexWorker.js`) with a main-thread fallback. The other modules are small, vscode-free pieces extracted from `DataService` (history state machine, bad-line tracker, file writer, backup recovery, exporter, engines, registry, stale watch, logger) so each can be unit-tested with temp files only. Nothing in this directory imports `vscode`.

## For AI Agents

### Working In This Directory

- No `vscode` imports here. `indexWorker.ts` and everything it imports must also stay free of `vscode` (it runs in a worker thread and is bundled separately).
- Memory bounds. Never read a whole file. All reads are byte ranges through `LineIndex` / `ByteReader`; file moves/copies use `WRITE_BLOCK_SIZE` (4MB) chunks. Every result list has a cap (`SEARCH_MAX_RESULTS`/`FILTER_MAX_RESULTS` 50k, `MAX_SELECTION_LINES` 5k, `MAX_EXPORT_LINES` 50k, `MAX_BAD_LINES` 20k, `RECORDS_MAX_COUNT` 2000, `COPY_MAX_BYTES` 8MB, history 50 entries / 16MB, replace-undo `MAX_REPLACE_UNDO_*`). Any new limit goes in `../constants.ts` and must surface as an explicit `truncated`/`skipped` field.
- Cancellation. Long operations take `shouldCancel?: () => boolean` and `onProgress`. Progress is throttled with `throttleProgress` (every `PROGRESS_THROTTLE_MS`, final tick always sent). Distinguish `cancelled` (scan incomplete, result untrustworthy) from `truncated` (result is a valid prefix). Never cache a result with either flag set. Never apply batch writes on a `cancelled` or `truncated` search (`replaceText` refuses both).
- Write safety.
  - Every disk-mutating public method goes through `runExclusive` (the `writeChain`). Public entry points lock; `*Internal` methods never lock (history replay calls them inside the lock, so taking it again self-deadlocks). `exportLines` is deliberately outside the chain and outside history.
  - Variable-length single-line writes must keep the tail backup: `<file>.jlv-tail-bak` and `<file>.jlv-tail-bak.json` are written before any shifting, backup starts at the edited line's start, and both are removed only after success or a successful rollback. Cancel triggers `rollbackToBackup`; if that fails the sidecar is kept and the error says where.
  - Batch rewrites (`rewriteWithEdits`) use a same-directory temp file plus atomic rename; the temp file must be in the same directory. Release both file handles (`releaseFileHandles`: main reader and host reader) before the rename and always re-acquire in `finally` (Windows EPERM otherwise).
  - Conflict checks (`detectWriteConflict`): `expectedTotalLines` (caller view) first, then size/mtime against `snapshot`. `expectedBytes` on `editRecord` is the per-record optimistic lock. Pretty/multiline files use record numbers and `recordRange`; `replaceText` rejects multiline files.
  - Public edit input must be a single physical line and valid JSON; the history replay path (`editRecordInternal`, `insertRecordInternal`) intentionally skips the single-line check so multi-line originals can be restored.
  - After a write, verify by reading back (`verifyAfterRecordEdit`) and roll back on failure.
- Index consistency. There are two `LineIndex` copies: `DataService.index` and the one inside the `IndexHost`. Only `stageIndexOps`/`commitIndex` may change `this.index` after a write, and `refreshSnapshot` is the one place that flushes ops to the host, invalidates `badLines`, and clears `queryCache`. Multiline files skip incremental ops and call `rebuildIndex()`. `rebuildIndex` must dispose the previous host (otherwise workers leak and `activeWorkers` never decreases). A failed flush sets `hostDirty`; `search`/`filter` rebuild first via `ensureFreshHost`.
- Worker bundle and fallback. The worker script is `dist/indexWorker.js`, passed in by `extension.ts` as `workerScriptPath` (`path.join(extensionPath, 'dist', 'indexWorker.js')`). `new Worker(missing)` does not throw synchronously, so the real fallback is `buildIndexWithFallback` (retry on the main thread after a worker failure), not the `try/catch` in `createIndexHost`. At most `MAX_ACTIVE_WORKERS` (8) workers; beyond that new hosts run on the main thread. Adding a request type means updating `workerProtocol.ts`, `indexWorker.ts` (including `requestId` on its `error` reply), `WorkerIndexHost` and the fake worker in tests.
- History cursor. `EditHistory` has one cursor. VS Code undo/redo, the history panel and `revertTo` all go through `DataService.undoStep`/`redoStep`/`setHistoryCursor`; do not add a second stack. `history.applying` suppresses pushes during replay. `dispose()`/`reload()` clear history because offsets are invalid afterwards.
- Bad lines. `BadLineTracker.lines` only contains rows that were read, sampled or scanned. `getBadLines().partial` is true unless `scanBadLines` finished and nothing has been written since. Content changes call `invalidate()` (keep the list, drop `complete`); a cancelled scan must not replace the list. The scan's notion of "bad" must match the list's red marks (oversized rows count as valid).
- Tail follow. `tryTailAppend` only runs for a compact, `eof`, newline-terminated index with no pending `indexOps`, growth within `TAIL_APPEND_MAX_BYTES`, and a matching 256-byte `tailAnchor` fingerprint. Any doubt returns `null` and the stale banner takes over.
- Comments are Chinese and explain the incident behind each guard; keep new comments in Chinese and preserve existing ones when refactoring.
- No constructor parameter properties; assign fields in the constructor body.

### Testing Requirements

- Every module here has a test in `__tests__/`; new behavior needs a test next to the existing one. Run one file with `node --experimental-transform-types --test src/host/__tests__/<file>.test.ts`; whole suite with `pnpm test`; coverage gate with `pnpm test:coverage:gate`.
- Write-path tests should follow the "edit, then query, then compare disk bytes" shape (see `dataServiceHostSync.test.ts`): a bug that desynchronizes the two indexes only shows when both are exercised.
- Use `hostFactory` / `WorkerLike` fakes to observe host lifecycle instead of spawning real workers, except where `indexHostFallback.test.ts` intentionally points at a non-existent worker script.

### Common Patterns

- Failure results are structured (`DataService.editFailure`, `replaceFailure`, `deleteManyFailure`, `{ ok: false, error, conflict?, cancelled?, invalid? }`); only unexpected errors throw.
- `*Internal` / public-entry split with `runExclusive`.
- `editing = true` during a write so `checkStale` returns `null`; always reset in `finally`.
- Generation counter (`this.generation`) invalidates an in-flight `ensureIndex` after `dispose`/`reload`.
- Cached query results are cloned on the way out (`cloneSearchResult`/`cloneFilterResult`) and keyed on `size:mtime` plus the query.
- Pure state machines (`EditHistory`, `BadLineTracker`) are kept free of IO so their rules can be tested without files.
